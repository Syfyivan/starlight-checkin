3.25.0 增加长期专项分期、事先约定的逾期处理，以及双方确认的免新增利息补还方案。领奖人入口显示为“借币与分期”：先用日常语言说明借币、分期、利息和还不上时怎么办，确认页突出总额与日期；计算公式和详细信用数字折叠展示。

3.24.1 将未完成扣分改为三选一，入口为「发奖管理 → 小屋规则 → 每日学习约定」。默认每项固定 2 币；也可选每项任务分值的 10%，或每项当天任务所得的 2%。已有自定义数值保留，不再强制把固定币数与收入比例取较高值。

- 可选未完成梯度，默认关闭。开启后第 1–2 项按原额、第 3–4 项乘 1.5、第 5 项起乘 2；按任务分值扣时，高分项先用低档，任务顺序不影响结果。当天收入 100 币、漏做 3 项时，2% 模式关闭梯度扣 6 币、开启扣 7 币。

3.24.0 增加每日学习约定。新规则从更新后的北京时间次日开始，不追补此前的空白天；新加入小屋当天不参与。旧扣分明细原样保留。

- 没计划也会结算：没有完成任务、累计专注不足 10 分钟、没有阅读笔记或读完记录时，默认按连续未学习 5／10／15／20 币逐日计算，以后每天最多 20 币；有学习记录当天清零连续天数。只登录、领礼物、宠物旅行不算学习。
- 未完成任务按每项最低 2 币与当日任务所得 1% 较高值，合计每天最多 20 币；与未学习扣分取较高项，不叠加。普通任务每天检查，重复任务按周期，长期任务只看截止日；长期任务的专注时间可证明当日有进展。
- 只扣现有正余额，不新增或扩大待补余额，不扣经验和共享金币。余额为零仍保留连续天数和预计扣分记录，以后不补收那一天未扣的金额。
- 发奖人在“小屋规则 → 每日学习约定”调整首日扣币、每日加扣、每项最低扣币、收入比例、每日上限或关闭规则。修改先结算过去日期，历史不重算；次日可退回实际扣款，保留通知与日志。家庭各人独立，个人空间和家长发奖家庭的管家不参与。
- 首页提供一行结算预估，学习币附近可展开规则；没有任务的日子也把结果发到本人和本屋发奖人的日报。服务每分钟处理跨日结算，停机后的补结算与重试不会重复扣币。

3.23.0 在「借贷与分期」增加小屋信用、按收入测算额度、长周期分期和大额申请。原有合同的本金、利率、还款日期不变；规则只约束新借款。

- 额度取发奖人设置、信用档位、还款能力的最低值。档位为 300／800／1500／3000／5000 币，按近 28 天实际观察到的完成率、有完成记录的天数及按期偿还记录逐步开放。最高档还要求一笔实际占用至少 7 天的按期结清记录；减免或当天借还不算。没有借过钱不算不良记录。
- 稳定日收入取最近 14／28 个完整自然日净任务所得均值中的较低值，零收入日照常计入。排除借款、赠币、全勤和长期任务的一次性高分；每期本息不超过对应天数稳定收入的 40%。没有足够收入时实际可申请额可能是 0，并展示原因。
- 当天观察到的到期任务留快照，跨日冻结，后续编辑或归档不能抹掉已经过去的约定；休息日和未到期长期任务不算漏做。旧数据缺少当时计划快照时标为未知，不伪造完成率。评估只给本人和本屋发奖人查看。
- 现金借款保留 7／14／30 天到期，另可选 3／6 期、每 30 天一期。商城分期可选 3／6 期、每 7 或 30 天一期。这里的 30 天是固定天数，不是自然月；签约前显示每一期准确日期和金额。
- 超过 1000 币须由另一位发奖人逐笔同意。申请 7 天有效，可撤回；申请与批准均不发币、不锁库存。本人收到同意后，重新预览并确认实际还款日期才会到账或发卡。签约时再检查规则、奖品、还款能力和批准人的当前权限。
- 家庭管家不能批准自己的申请。各人的余额、债务和评估独立，普通家庭成员看不到他人的评估。逾期不加罚息，只暂停新借款并影响近期的额度档位；已经确认的合同不追改利率。

没有新增依赖。借贷入口仍在学习币账本和商城，发奖人从「小屋规则」进入；申请通知中的按钮可直接打开对应小屋。数据库增量迁移到 schema 23。

3.22.0 增加学习币借贷与商城分期。双人小屋和家庭默认关闭，由发奖人在「发奖管理 → 小屋规则 → 借贷与分期」开启；领奖人在学习币账本或商城进入，支持的奖品下方显示「查看分期方案」。个人空间暂不开放。

- 默认每人每间小屋额度 300 币、年化单利 6%，可由发奖人调整。6% 是模拟设置，参考的 [2026 年 10 月 20 日一年期 LPR 为 3%](https://www.chinamoney.com.cn/chinese/rdgz/20261020/3433485.html)，不是个人实际贷款报价。这里只有平台积分，不产生人民币债务。
- 借款选择 7、14 或 30 天；个人报销卡及约定体验可全额分 3 或 6 期，每 7 天一期、等额本金。签约前展示每期本金、利息上限与总额，报价 5 分钟有效；规则、奖品或日期改变后须重新确认。
- 按北京时间自然日差、年 365 天计算，借款当天为 0 天。整数账本精确到百万分之一币，累计计息向下取整。每期到期后停止新增利息，合同总利息不超过确认时的上限；没有手续费、复利或罚息。
- 手动偿还到期款，余额不足可部分偿还，按最早到期账单逐期先息后本；也可提前全部结清并免除未来利息。不自动扣币，不支持任意提前部分本金还款。借来的币不增加经验、任务收入或每日扣分基数。
- 每人每间小屋只保留一笔未结清合同，期间暂停学习币抽奖，免费机会可用；逾期后暂停商城消费，做任务、还款和原有卡片核销仍可进行。发奖人可说明原因后减免，记录日志并发信通知；家庭管家不能减免自己的债务。
- 家庭共用借贷规则，个人余额和债务独立。普通家庭成员看不到别人的借贷合同。关闭小屋或转为仅发奖身份前须先结清；修改规则只影响新合同。

## 本期功能

- 任何人可直接注册。每段发奖/领奖关系各有独立小屋；同一账号可同时收奖、发奖并继续邀请多位伙伴，权限不沿关系传递。
- 每日重复和单次计划、未来计划、分类、完成心得、归档。
- 手动添加、Markdown 粘贴与文件、TXT / CSV / JSON 导入，支持普通列表和四象限，预览后提交；最多 50 项、256 KB。
- 完成时选择难度或填写分数；当天可改分，账本只补发或扣回差额。每日上限只限制发币，不阻止任务完成或全勤。取消仅支持当天，历史不改写。
- 奖励小屋默认全勤送 1 次免费抽奖；发奖人可改为额外学习币、调整数量或关闭。每天每间小屋一份；撤销会收回，重新完成恢复原奖励，已用机会记待补。免费机会可累积，不占学习币抽奖的每日次数。
- 学习币花掉后仍能撤销任务；负余额先补足再消费和兑奖。
- 43 种报销模板，从 ¥2/¥5/¥10 起，另有 20 学习币的小屋改名卡；默认卡一键添加、单张/整套移除与恢复，重复添加不重置库存。
- 积分商城和独立随机抽奖；发奖人可按百分比设置每张卡的中奖率，缺货概率转为未中奖，完整概率公开。抽奖与商城分开库存，可复制但不联动；升级后独立奖池由发奖人确认布置。
- 七种报销品类和万能卡，名称、面额、等级、样式、库存及售价可自定义；同品类可加入万能卡合成：等额卡合计 × 1.25，不等额卡只有最小一张加 25%，最终向上取整到元；万能卡转换仍然等额，同源拆分卡不能合回赚加成。
- 发卡时预留库存；成员提交购买/充值说明和可选图片，生成分享链接，直接发奖人确认现实中已报销后核销。
- 配对发奖人设置奖励、币名、每日上限、抽奖规则和市场解锁门槛；不同配对规则独立。
- PWA 主屏幕图标、手机底部导航与离线提示；GitHub 和验证邮箱登录需要真实服务配置。
- 学习币收支明细、个人记录导出、基础货币/账本/概率/区块链小知识。
- 模拟市场默认累计 500 学习币达成门槛，扣除撤销任务，消费不影响进度。**交易未开放**，交易接口拒绝请求。

## 本地运行

需要 Node.js 22.13 或以上（内置 `node:sqlite`；22.x 会提示实验性 API 警告）。无需 `npm install`。

```powershell
npm start
```

打开 http://127.0.0.1:3210/，直接注册自己的账号，无需初始化口令或邀请码。密码需至少 10 个字符。邮箱验证、邮箱绑定和 GitHub 登录需要配置服务后启用，详情见 V2-HANDOFF.md；尚未实现邮件找回。

独立演示：`npm run demo`。第二版示例数据库为 `data/demo-v2.sqlite`，正式数据库为 `data/starlight.sqlite`。旧 `data/demo.sqlite` 保留但不再作为默认演示库。示例账号可在“我的小屋与伙伴”切换小凡、小芽和晴天。不要把演示数据库发布到公网。演示模式在配置公网地址时拒绝启动。

`npm test` 运行隔离的资金、库存、权限、持久化与 HTTP 检查；`npm run check` 做语法检查。

## 新用户怎么用

1. 注册自己的账号、昵称和密码，先进入仅自己可见的个人计划。
2. 在“我的小屋与伙伴”选择“邀请朋友给我发奖”或“邀请朋友来我这领奖”；系统生成一次性邀请码，也可复制邀请链接，7 天有效。对方核对身份并确认后新建一间空小屋。
3. 发奖人切换到对应小屋，选择奖励模板或自定义卡片，设置能承担的库存与规则。
4. 领奖人在对应小屋添加或导入计划，完成后勾选。
5. 商城或抽奖获得卡片，可合成/转换；拿购买或充值记录申请报销，把核销链接交给发奖人。
6. 发奖人完成现实中的报销或发放后，在链接弹窗或工作台确认核销。

CSV 格式：`任务名称,奖励,重复方式,分类,开始日期`。重复方式为“每天”或“单次”，开始日期可留空；JSON 字段为 `title, points, recurrence (daily/once), category, start_date`。TXT 一行一个任务，默认单次、20 币。

## 腾讯云部署

可复用现有 Docker 和 Caddy。只发布一个独立容器，监听 `127.0.0.1:8801`，经现有 HTTPS 的 `/starlight/` 子路径访问。

Windows 发布使用 `deploy/ssh-session.ps1`，由 Microsoft OpenSSH 调用本机 1Password SSH Agent。脚本只使用本机 `.ssh/tencent-booking.pub` 选择公钥，不读取 1Password CLI、不导出私钥。可通过 `-PublicKey` 和 `-Destination` 指定其他公钥文件与目标。

在 1Password 的“设置 → 开发者 → SSH Agent 高级设置”中，把批准范围设为“每个新应用”，记住批准设为“24 小时”。首次连接由本人批准；锁定后仍需本人解锁，退出 1Password 会结束代理会话。不要勾选“批准所有应用”。[官方授权说明](https://www.1password.dev/ssh/agent/authorization)。

```powershell
pwsh -NoProfile -File deploy/ssh-session.ps1
```

脚本输出 `CLOUD_SESSION_READY` 后，每行输入一个 JSON 请求，例如 `{"action":"ssh","command":"true"}`。上传使用 `{"action":"upload","source":"C:/path/release.tar.gz","target":"/tmp/release.tar.gz"}`；退出使用 `{"action":"stop"}`。检查每条请求的 `SSH_EXIT` 或 `UPLOAD_EXIT`，只有 `0` 表示成功。它只提供连接，不会自动部署或修改服务器。

```sh
docker build --pull=false -t starlight-checkin:3.2.3 .
sudo PUBLIC_ORIGIN=https://your-domain.example IMAGE=starlight-checkin:3.2.3 sh deploy/run-container.sh
```

将 `deploy/starlight.caddy` 导入已有的 HTTPS 站点块。修改前备份 Caddyfile；先 `caddy validate --config /etc/caddy/Caddyfile` 再 reload。不要覆盖其他站点。默认 URL 的端口必须和 `PUBLIC_ORIGIN` 完全一致。

配置：

| 配置 | 用途 |
| --- | --- |
| `PUBLIC_ORIGIN` | 完整 HTTPS 源，如 `https://example.com`；校验写请求来源并启用 Secure Cookie |
| `BASE_PATH` | Cookie 范围，子路径部署为 `/starlight/` |
| `HOST` / `PORT` | 容器内为 `0.0.0.0:3210`；宿主机仅映射到回环地址 |
| `DB_PATH` | `/var/lib/starlight/starlight.sqlite`，持久化挂载 |
| `TRUST_PROXY` | 本机 Caddy 后设为 `1`，用于登录频率限制的客户端地址 |

网站开放注册，不再读取或生成初始化口令；旧 /api/setup 返回 410。昵称允许重复，登录账号唯一，内部账号和小屋使用系统 UUID。邀请码使用 96 位随机值、数据库唯一约束与碰撞重试，只创建指定的两人关系，不是万能空间访问密码。

数据库目录独立于版本目录；发布和回滚不能覆盖它。容器采用非 root 用户、只读根文件系统、资源限制和自动重启。没有改动宿主机已有 Node.js，也无需新数据库服务。

### 备份与恢复

`docker exec starlight-checkin node scripts/backup.mjs` 使用 SQLite `VACUUM INTO` 生成一致快照，不直接复制仍在写入的 WAL 文件。快照位于 `/var/lib/starlight/backups/`，权限 600。

可安装随附 systemd timer，每天北京时间约 04:15 备份。没有自动删除旧备份；应定期检查磁盘容量，并把备份复制到自己控制的异机存储。同机备份不能防止服务器磁盘故障。

恢复：停止 **starlight-checkin 这一容器**，备份当前整个数据目录，再用选定快照替换主数据库并保留正确所有者；旧 WAL/SHM 文件应随原目录一起留存，不可与快照混用。重新启动后验证健康、账号与账本。

升级：第二版提供事务式数据库迁移及 `deploy/upgrade-v2.sh`。先验证新镜像，再停止本应用、备份最终数据库、保留旧容器并运行新容器。跨版本回滚必须同时恢复升级前数据库，不能把旧程序直接接到新数据库；参阅 V2-HANDOFF.md。

## 一致性与访问控制

余额由整数账本求和得到；每笔操作在 SQLite 事务中完成。客户端不能指定收入人或中奖结果；重复请求按用户和请求编号去重。同任务同日只有一个完成记录。奖品卡保存发卡时的内容，后续改奖品不影响已发卡。消费确认时检测售价/奖池是否变化；发奖人编辑检测库存是否被其他操作改变。

密码经带随机盐的 scrypt 哈希存储。会话令牌只存哈希，Cookie 为 HttpOnly/SameSite，公网另有 Secure；写操作校验来源和 CSRF。密码变化和停用账号会注销旧会话。数据库、环境变量和初始化口令不由静态服务暴露。

本系统适合小圈子自觉打卡；成员可自定任务和奖励，发奖人用每日上限约束供给。没有任务真实性审核，也没有充值、提现、借贷或用户间转账。
